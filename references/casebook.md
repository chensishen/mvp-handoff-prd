# MVP 交接型 PRD 案例库

以下是基于真实项目高频问题整理的脱敏合成案例。公司、人员和数字均为示例，不代表某个具名客户；案例的价值在于还原真实交接中的证据、冲突和门禁处理。不得把案例指标直接套到新项目。

## 案例一：内部 AI 会议纪要助手

### 交接现场

业务同事用 React 做出 MVP：上传音频后数秒内显示转写和摘要。提出的需求只有一句：“希望减少同事整理会议纪要的时间。”

代码审计发现：

- 上传页面确实可操作；
- `/api/transcribe` 返回固定 JSON，没有调用真实转写服务；
- 摘要结果为硬编码文本；
- 文件只保存在浏览器本地；
- 没有登录、权限、失败状态、删除机制、日志或监控；
- README 没有运行环境和依赖版本。

### 容易写错的 PRD

把“MVP 可以自动生成纪要”写成已实现能力，然后列出登录、历史记录、多人协作、模板管理等“待完善功能”。这同时犯了两个错误：Mock 被当成真实能力，MVP 缺少的内容被自动当成本期范围。

### 正确处理

| 内容 | 状态 | 处理 |
|---|---|---|
| 减少整理时间 | 已确认目标方向 | 成功指标和口径仍待业务 Owner 确认 |
| 上传后展示结果 | MVP 观察 | 只证明交互壳存在 |
| 转写能力 | 占位/Mock | 需要采购或接入真实服务 |
| 摘要能力 | 占位/硬编码 | 需要定义质量标准和人工编辑方式 |
| 登录、历史记录、多人协作 | 待确认 | 不自动加入范围 |
| 音频保存期限 | 待确认且阻塞 | 涉及个人信息与存储成本 |

初次门禁：`G1 FAIL / G2 FAIL / G3 FAIL / NOT READY`。

经过评审，业务确认本期只服务内部员工，采用公司 SSO；纪要必须允许人工编辑；原始音频保存 7 天后自动删除；多人实时协作和自定义模板不在本期。成功指标确定为“试点部门单次会议人工整理时长中位数从 30 分钟下降至 10 分钟以内，连续观察四周”。

### 需求卡片示例

`FR-001 上传音频并生成可编辑纪要`

- 来源：内部立项 DEC-003
- MVP 现状：上传 UI 已实现；转写和摘要均为占位
- 目标行为：已登录员工上传允许格式的音频后，系统创建处理任务并最终展示可编辑纪要
- 优先级：Must
- Owner：会议效率产品负责人

```gherkin
AC-FR-001-01
Given 员工已通过公司 SSO 登录，且准备一份 30 分钟、合法格式的音频
When 员工提交上传
Then 系统只创建一个处理任务，并依次显示“上传中、转写中、生成摘要、可编辑”状态
And 处理完成后员工可以编辑并保存纪要
```

```gherkin
AC-FR-001-02
Given 同一员工对同一文件重复点击提交
When 第二次请求携带相同幂等键
Then 系统返回原任务，不重复保存文件或创建计费任务
```

最终门禁只有在真实服务、权限、删除任务、失败恢复、监控和 Test 映射全部确认后才能变为 `DEVELOPMENT_READY`。

## 案例二：外部零售客户的订单导出工具

### 交接现场

客户合同写的是“支持按日期导出订单 CSV”。销售在聊天中说过“Excel、PDF 应该也能做”。需求同事制作的 MVP 有 CSV 导出按钮，但数据来自一份本地样例 JSON。

技术审计发现：

- 只验证了 20 条样例订单；
- 未连接客户真实订单 API；
- 没有客户租户隔离，URL 参数可以切换门店；
- 金额使用浮点数；
- 没有大批量导出、超时、失败重试或下载链接过期机制。

### 证据与冲突

| 事项 | 合同 | 销售聊天 | MVP | PRD 处理 |
|---|---|---|---|---|
| CSV | 明确承诺 | 已提及 | 有按钮 | 本期 Must，但真实数据链仍未完成 |
| Excel | 未承诺 | 模糊承诺 | 无 | 标记冲突，等待客户授权人书面决定 |
| PDF | 未承诺 | 模糊承诺 | 无 | 不自动进入范围 |

初次门禁：`NOT READY`，原因是客户验收范围和真实数据接口未确认。

客户随后书面确认：本期只交付 CSV，Excel 进入下一报价，PDF 不做；单次最多导出 50,000 条，超过后提示缩小日期范围；下载链接 24 小时失效。

### 验收标准示例

```gherkin
AC-FR-EXPORT-01
Given 客户门店管理员已登录，日期范围内有 50,000 条或更少的订单
When 管理员发起 CSV 导出
Then 文件只包含其有权访问门店的订单
And 金额以两位十进制字符串输出，订单数和金额汇总与订单 API 对账一致
```

```gherkin
AC-SEC-EXPORT-01
Given 用户属于门店 A
When 用户修改请求中的门店 ID 为门店 B
Then 服务端拒绝请求且不生成文件
And 安全审计日志记录用户、目标门店、时间和拒绝原因
```

这个案例中最重要的 PRD 作用不是描述“导出按钮”，而是固定合同范围、租户边界、数据精度、容量和客户签收口径。

## 案例三：内部销售经营看板

### 交接现场

销售运营同事用低代码工具制作看板，展示线索数、转化率、销售额和排行榜。管理层认为效果不错，要求技术团队“接成正式系统”。

审计发现：

- MVP 用个人数据库管理员账号直连生产库；
- 转化率分母在不同页面使用“全部线索”和“有效线索”两种口径；
- 销售额包含已退款订单；
- 排行榜按昵称关联，重名员工数据合并；
- 数据每天由发起人手工刷新；
- 没有数据更新时间、质量告警或血缘说明。

### 正确 PRD 裁决

- 现有页面布局可以作为设计参考，但指标数值不能作为可信基线；
- 指标定义先由销售、财务、数据 Owner 联合确认；
- 个人管理员账号必须移除，改为最小权限服务身份；
- 员工关联使用稳定员工 ID；
- 手工刷新不是正式生产流程；
- 在口径、权威数据源和历史回算范围确认前，G2 不通过。

### 数据需求示例

`DATA-003 销售额口径`

- 权威源：财务确认的结算订单事实表
- 计算范围：已结算且未全额退款订单
- 部分退款：以结算金额减已确认退款金额
- 时间口径：公司配置时区的自然日
- 更新频率：每小时完成一次增量处理
- 对账：每日与财务日报核对订单数、总额和退款额

```gherkin
AC-DATA-003-01
Given 某自然日存在一笔 100 元订单且已确认退款 20 元
When 看板完成该日数据刷新
Then 销售额贡献为 80.00 元
And 每日对账结果记录订单数、销售额和退款额差异
```

最终交接必须同时包含数据字典、指标 Owner、服务账号、刷新任务、数据质量告警和失败重跑 Runbook；仅把低代码页面重写成前端不算完成。

## 案例四：外部制造客户的巡检移动端

### 交接现场

现场顾问做了一个手机网页 MVP：选择设备、填写检查项、拍照、提交。客户提出“车间网络差，也要能用”。演示时手机一直连接办公室 Wi-Fi。

审计发现：

- 所谓“离线”只是页面已打开时还能填写，刷新后内容丢失；
- 图片保存在内存，关闭页面即丢失；
- 重复点击提交会产生重复记录；
- 工厂编号硬编码；
- 没有设备清单版本、离线数据加密、冲突处理和同步状态；
- 客户没有确认两名巡检员同时修改同一设备记录时以谁为准。

### 差距裁决

| 能力 | 当前 | 目标 | 处置 |
|---|---|---|---|
| 在线填写 | 部分实现 | 保留并补错误状态 | Complete |
| 真正离线草稿 | 未实现 | 本地持久化并可恢复 | Add |
| 照片离线保存 | 未实现 | 加密保存并进入同步队列 | Add |
| 同步幂等 | 未实现 | 每个巡检单使用稳定客户端 ID | Add |
| 冲突策略 | 未决 | 需客户现场负责人决策 | Blocking |

门禁维持 `NOT READY`，直到冲突策略、最大离线时长、设备清单版本和现场验收环境得到确认。

### 验收标准示例

```gherkin
AC-FR-OFFLINE-01
Given 巡检员已下载当日设备清单，随后设备断网
When 巡检员填写检查项、拍摄三张照片并关闭应用
Then 重新打开应用后草稿、照片和设备关联保持完整
And 页面明确显示“待同步”状态
```

```gherkin
AC-FR-SYNC-02
Given 同一巡检单已成功同步但客户端未收到成功响应
When 客户端恢复网络并重试同步
Then 服务端返回原记录且不创建重复巡检单或重复照片
```

OAT 还需要在真实或等价车间网络下验证断网、弱网、重启、存储不足、批量恢复和版本升级。

## 案例五：内部发票 OCR 报销助手

### 交接现场

财务同事做出 MVP：上传发票图片后自动识别金额、日期和发票号，并生成报销记录。演示识别率很好，计划直接交给技术岗位接入审批系统。

审计发现：

- 只使用 30 张清晰电子发票做过演示；
- OCR 服务使用发起人的个人账号；
- 发票图片写入公开对象存储桶；
- OCR 结果直接进入报销记录，没有人工确认；
- 同一发票重复上传会生成多笔记录；
- 没有记录原图、识别结果、人工修改和最终提交之间的审计链；
- 财务尚未确认增值税发票、卷票、外币票据和红字发票的范围。

### 正确范围

不能把“识别率很好”写成事实，也不能让 OCR 自动批准报销。初版范围应先由财务确认票据类型和人工复核规则。

建议的核心决策：

- OCR 结果始终作为候选值，由员工确认后提交；
- 使用发票代码、号码、金额、日期等组合做重复风险提示，但最终处置规则由财务确认；
- 原图使用受控存储、短期访问链接和明确保留期限；
- 记录 OCR 原值、人工修改值、修改人和时间；
- OCR 供应商账号、数据处理地域和删除责任必须由公司账户承接。

### 验收标准示例

```gherkin
AC-FR-OCR-01
Given 员工上传一张本期支持类型的发票
When OCR 返回金额、日期和发票号
Then 系统以“待员工确认”状态展示识别值
And 在员工确认前不创建正式报销单或触发审批
```

```gherkin
AC-SEC-OCR-01
Given 发票图片已经上传
When 未授权用户直接访问对象地址
Then 存储服务拒绝访问
And 授权下载链接在规定时间后失效
```

该项目在票据范围、重复票规则、保留期限、供应商数据处理条款和财务验收人未确认前必须是 `NOT READY`。

## 五个案例的共同规律

1. 演示成功路径最容易掩盖 Mock、硬编码、个人账号和手工操作。
2. MVP 有什么，不等于正式产品就应该保留什么。
3. MVP 没什么，也不等于本期必须补什么。
4. 外部项目常见风险是合同、销售承诺和客户口头期待冲突。
5. 内部项目常见风险是指标口径、数据 Owner 和长期运营归属不清。
6. 真正阻塞开发的往往不是页面，而是权限、数据、异常恢复、合规、验收和发布责任。
