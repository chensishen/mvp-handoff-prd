# 交接型 PRD 系统流程

## 1. 系统目标

本流程服务于一种特定交接：需求提出者已经做出 MVP、原型或项目骨架，但实现不完整；随后由 C 技术岗位把它补成可交付产品。PRD 的职责是把“需求意图、MVP 事实、目标差距、验收契约”连成一条可追踪链路。

核心公式：

`最终交接范围 = 已确认目标 - 经验证的 MVP 现状 + 必要质量要求 + 发布运营要求`

MVP 中出现的功能不自动等于目标需求；MVP 中缺少的功能也不自动等于本期范围。

## 2. 角色与责任

| 角色 | 主要责任 | 不应被默认承担的责任 |
|---|---|---|
| 需求提出者 | 解释问题、目标、业务规则，确认取舍 | 仅凭 MVP 替代完整需求说明 |
| 产品/PRD Owner | 维护证据、范围、决策、追踪与版本 | 擅自决定客户承诺或技术工期 |
| C 技术岗位 | 审核可行性、技术方案、估算、实现与自测 | 猜测未确认业务规则 |
| QA/验收人 | 建立用例、验证 AC、记录偏差 | 用“看起来没问题”代替证据 |
| 客户/业务 Owner | 确认价值、范围、关键规则和最终接受 | 把口头新增内容视为已纳入范围 |
| 运维/安全/合规 | 审核生产质量与专项风险 | 在上线前最后一天才被动接手 |

小团队可一人兼任多个角色，但签字责任仍需明确。

## 3. 双入口：外部与内部

### 外部客户需求

优先级从以下来源建立：已签合同/订单或正式变更单 > 客户书面确认 > 评审纪要 > 访谈/聊天 > MVP 表现 > 推断。

必须额外确认：

- 客户组织、最终用户与验收人是否相同；
- 明示承诺与隐含期待的边界；
- 交付形式、客户环境、集成方、数据归属与迁移；
- SLA、合规、品牌、培训、文档和支持责任；
- 需求变更如何报价、排期、签认。

### 内部项目需求

优先级从以下来源建立：公司/部门目标与正式决策 > 业务 Owner 确认 > 已批准立项 > 流程与数据事实 > MVP 表现 > 推断。

必须额外确认：

- 目标与 OKR/经营指标的关系；
- 使用人、受影响团队、流程变化与培训；
- 与现有系统、权限、主数据、报表的关系；
- 上线后的产品、技术、运营、数据 Owner；
- 机会成本，以及不做/延期的影响。

## 4. 六阶段流程与产物

### 阶段 A：资料归集与证据化

输入：需求材料、MVP、代码、设计、沟通记录。

动作：

1. 建立资料清单并记录版本、日期、来源人。
2. 提取目标、用户、规则、约束、承诺、术语。
3. 给每条信息标记状态与可信度。
4. 建立冲突表与待确认表。

出口：资料能追溯；关键角色和决策权明确；敏感信息已处理；通过 `CP-A Evidence Frozen`。此阶段只分类与标注缺口，不用 AI 补全业务规则。

### 阶段 B：MVP 逆向审计

输入：可访问的产品、代码和环境。

动作：

1. 从用户主流程开始实测，再下钻页面、接口、数据和代码。
2. 把“实现状态”与“质量状态”分开记录。
3. 标注 Mock、硬编码、临时数据、跳过的鉴权、未处理异常。
4. 记录构建、测试、部署、监控、回滚现状。

出口：任何“已经有”的判断都有证据；未知项有影响说明。

### 阶段 C：目标与差距定稿

输入：已确认需求 + MVP 基线。

动作：

1. 定义问题、目标、指标和用户。
2. 划分 In/Out/Later，并按价值、风险、依赖排序。
3. 对 MVP 每项作保留/修改/移除/待定决策。
4. 形成目标差距与交付批次。
5. 由产品/业务 Owner 确认目标主流程，AI 仅拆解操作、响应、状态和数据副作用。

出口：范围能估算，且不存在“默认都要做”的模糊区域；通过 `CP-B Main Flow Approved`。

### 阶段 D：规格化与可测试化

输入：已确认范围。

动作：

1. 先按主流程节点做“只提问题、不给结论”的异常、边界、权限、冲突、依赖与恢复排查，由授权人确认规则并通过 `CP-C Rules Decided`。
2. 建立编号化需求、规则、非功能要求和验收标准。
3. 补齐流程、状态、权限、接口、数据、异常和边界。
4. 为 Must 项建立需求—设计/代码—测试—发布追踪。
5. 把不确定内容留在决策日志，不埋进正文。
6. 补齐 C 岗实施上下文：代码路径、现有模式、任务边界/依赖和可执行的验证命令。

出口：C 岗位可以估算和拆任务，QA 可以直接设计测试；通过 `CP-D Spec Compiled`。分阶段详细见 [staged-authoring.md](staged-authoring.md)。

### 阶段 E：跨角色评审与门禁

至少进行产品、技术、QA 三视角评审。高风险项目加入安全、合规、运维、数据评审。

普通评审顺序：先暴露问题 → 决策人选择 → PRD Owner 回填 → 复核追踪关系。

对客户承诺、核心业务规则、技术估算和风险接受，按 [decision-assurance.md](decision-assurance.md) 先验证授权与证据，再检查合同/法规/流程/数据/代码基线的一致性、可行性、影响、剩余风险和失效条件。签字不自动代表正确；越权、证据冲突或不可执行仍应判 `INVALID`。

若用户要求专家团，或项目为 L2/L3、跨系统/合同边界复杂、核心规则存在争议，使用 [expert-panel.md](expert-panel.md) 的独立两轮法：共同证据包 → 专家独立首轮 → 去重并暴露分歧 → 定向复核 → 具名责任人裁决 → 回填复核。专家团不通过多数票替代客户、业务 Owner、C 技术负责人或专项风险 Owner。

出口：通过 Development Ready 门；未通过时给出阻塞 ID 与责任人，不伪装完成。

### 阶段 F：交接、变更与发布

交接不是发一个链接。需完成 Walkthrough，确认代码/环境权限、基线版本、任务拆分、负责人、发布与回滚方案。

变更流程：提出变更 → 记录原因与来源 → 影响分析（范围/成本/工期/风险/验收）→ 决策 → 更新版本及所有关联 ID → 通知受影响角色。

已批准基线上的变更必须进入 [change-control.md](change-control.md) 定义的增量变更包。不用整篇重写来覆盖历史，也不在未批准前把提案变成开发承诺。

出口：交接双方确认；发布、监控、回滚、支持与复盘安排清楚。

## 5. 建议节奏

- 小型功能：一次资料/MVP 审计，一次联合评审，一次交接会。
- 中大型项目：基线评审、范围评审、规格评审、发布准备评审分别进行。
- 任何规模都不能跳过 MVP 基线、范围边界、验收标准和待决策日志。

## 6. 按风险裁剪深度

- `L0`：纯原型，不接真实用户或真实数据。可简化运维内容，但要明确不可上线。
- `L1`：低风险内部工具。保留身份权限、数据、基本监控、备份和回滚。
- `L2`：客户可见、生产使用或处理敏感数据。默认使用紧凑三件套和全部门禁；仅按归档、权限或独立签署要求拆文件。
- `L3`：资金、医疗、强监管、关键基础设施或高价值系统。增加独立安全、隐私、恢复和合规评审。

风险级别只影响深度，不取消证据基线、范围边界、验收和责任人。

| 交付模式 | 典型风险 | 最低要求 |
|---|---|---|
| QUICK | L0/L1 且改动小、可快速回滚 | 仍生成三件套；不适用的高级章节写 `N/A + 理由`，CP-A–D、Must AC、追踪与三方签署不取消 |
| STANDARD | 一般生产、内部关键流程或普通客户项目 | 紧凑三件套、产品/技术/QA 评审、实施上下文与发布验证 |
| HIGH_ASSURANCE | L2/L3、复杂合同、敏感数据、资金/医疗/强监管 | STANDARD + 专家团、独立安全/恢复/合规评审、更严格变更与证据要求 |

初始化器用 `--mode` 固化选择；`HIGH_ASSURANCE` 自动生成专家团记录并在未显式指定时采用 L2，任何显式 L2/L3 也自动生成该记录。模式控制内容深度和评审，不改变三件套的唯一真相源。紧凑版与扩展版不得混放在同一目录。

## 7. 失败模式

- 把演示路径当完整业务流程；
- 把硬编码、Mock 或手工操作当已实现；
- PRD 只写新增功能，不写 MVP 应保留/改造/删除什么；
- 需求按页面描述，缺少跨页面状态、权限、数据与错误恢复；
- 非功能需求写“高并发、稳定、安全”，没有指标和测量条件；
- AC 复述需求，没有前置条件、可观察结果和数据边界；
- 待确认项散落全文，无 Owner、期限和阻塞级别；
- 需求方给技术工期，实施者未评估；
- 发布计划没有迁移、灰度、监控和回滚；
- 口头变更覆盖旧决定，文档与任务系统失去一致性。
