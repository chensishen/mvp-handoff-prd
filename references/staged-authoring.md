# 分阶段 PRD 编写与人工检查点

本流程把 `AI写PRD指南.md` 的“归集 → 拆解 → 查错 → 定稿”改造为适合已有 MVP 交接的可审计过程。四阶段可以在一次任务中连续完成，但不得跳过检查点或把后一阶段的推测倒灌成前一阶段的事实。

## A. 信息归集：只分类，不补全

输入：原始需求、会议/聊天、合同/立项、MVP 运行与代码证据。

输出：证据、已确认信息、MVP 观察、合理推断、待确认、冲突。每条记录保留来源、日期、版本和提供者。

禁止：补业务规则、设定无依据指标、把 MVP 行为当成意图、用“行业通常”填空。

检查点 `CP-A Evidence Frozen`：证据包版本已记录；核心冲突与待确认项有 Owner；敏感信息已脱敏。

## B. 主流程拆解：人定方案，AI 拆细节

入口条件：产品/业务负责人给出或明确确认主流程。若只有 MVP 演示流程，将其标为“MVP 观察候选流程”，不得直接确认。

每个节点拆解：角色与前置、用户操作/事件、系统响应、页面/领域状态、数据副作用、下一节点。此阶段可指出正常分支缺口，但不处理异常规则。

检查点 `CP-B Main Flow Approved`：主流程 Owner 具名；版本与日期已记录；未确认备选方案已移入决策日志。

## C. 漏洞排查：只提问题，不替负责人决策

按流程节点检查：空状态、输入边界、无权限、重复/并发、超时/重试、依赖失败、部分成功、状态冲突、数据不一致、降级与恢复。另检查权限、规则优先级、API/数据契约、安全隐私、迁移发布与回滚。

发现项只能包含：问题、证据、影响的流程/需求 ID、严重度、建议决策人和是否阻塞。可列选项供决策，不得把选项写成结论。

检查点 `CP-C Rules Decided`：P0 已关闭；所有核心规则有授权结论；未决的非核心项有 Owner、期限、临时控制和阻塞级别。

## D. 规格编译：把确认内容编译成可实现契约

只使用 A–C 阶段的已确认内容。将来源、目标、MVP 差距、功能/规则/非功能要求、AC、测试、发布与决策连成可追踪链。资料仍缺失时保留待确认，不为追求“完整文档”而脑补。

检查点 `CP-D Spec Compiled`：每个 Must 需求可理解、可行、可验证；主流程版本与 PRD 一致；追踪矩阵无孤立引用；通过对应风险模式的评审。

## 阶段返回规则

- C 阶段发现主流程缺口，返回 B，不在 C 阶段自行修补。
- D 阶段发现无来源规则，返回 A/C，不把它包装成“默认行为”。
- 任一检查点未通过，可以继续形成草案，但不得声称下一门禁已通过。
