# 交接型 PRD 写作标准

## 1. 需求句式

优先写可观察的系统行为：

`当 <前置/触发> 时，系统应为 <角色> 提供 <行为/结果>，并满足 <约束/阈值>。`

避免把实现方案写成需求，除非它是已确认约束。避免复合句；一条需求只承诺一个主要行为。

## 2. 单条需求字段

| 字段 | 要求 |
|---|---|
| ID/标题 | 稳定、唯一、短标题 |
| 来源与理由 | 对应资料/决策/用户问题 |
| MVP 现状 | 状态、证据、置信度 |
| 目标行为 | 明确的应然状态 |
| UI 规格（适用时） | 原型/设计链接、页面/组件、关键文案、交互跳转、加载/空/错误/无权限状态 |
| 优先级 | Must/Should/Could/Won't |
| 规则与约束 | 计算、限制、状态、权限 |
| 异常与边界 | 空、错、慢、重复、并发、越权、恢复 |
| 依赖 | 上游/下游/第三方/数据/环境 |
| 验收标准 | AC ID 与可执行条件 |
| 状态 | 已确认/待确认/冲突/废弃 |

## 3. 验收标准

推荐格式：

```text
AC-FR-001-01
Given <可建立的前置条件>
And <必要数据/权限/系统状态>
When <单一动作或事件>
Then <外部可观察结果>
And <持久化、事件、日志或副作用>
```

要求：

- 结果可由 UI、API、数据库、事件、日志或指标客观观察；
- 数值包含单位、阈值、统计口径、样本/窗口与测试环境；
- 错误场景写明状态码/提示/是否重试/数据是否变化；
- 时间相关行为使用明确时钟条件；
- 一个 AC 尽量验证一个核心结果。

## 4. 流程、状态与权限

- 主流程：入口、前置、步骤、系统响应、结束状态。
- 分支/异常：从哪个节点分叉、触发条件、恢复或终止点。
- 状态机：状态、允许事件、守卫条件、目标状态、禁止转换。
- 权限矩阵：角色 × 资源 × 动作 × 数据范围；UI 与后端执行一致。
- UI 密集功能：补充原型/设计版本、页面元素、正常交互、页面跳转、加载、空数据、错误、无权限和恢复状态；纯后端需求写 `N/A + 理由`，不要制造空章节。

## 5. API 与数据

API 至少写：调用方/提供方、环境与版本、认证、请求、响应、错误码、幂等、超时/重试、限流、兼容与弃用策略。

数据至少写：实体/字段、类型、必填、默认、唯一/关联约束、来源、读写方、保留/删除、敏感等级、迁移/回填、审计要求。

## 6. 非功能需求

只保留适用项，并写成可测量目标：

- 性能：用户旅程或接口、负载、数据规模、p95/p99、测量点；
- 可用性：SLI、SLO、统计窗口、排除条件和责任动作；
- 容量：峰值并发/吞吐、增长假设、限额与降级；
- 安全：认证、授权、输入、会话、密钥、日志、漏洞等级；
- 隐私：目的、最小化、同意、留存、导出/删除、跨境；
- 可访问性：目标标准和级别、适用页面、验证方式；
- 兼容性：明确平台、版本、分辨率和降级策略；
- 可观测性：指标、日志、追踪、仪表盘、告警条件、Owner；
- 可维护性：测试门槛、依赖政策、文档和运行手册。

不要凭空设置“2 秒”“99.99%”等数字。来源不明时写候选值并进入决策日志。

## 7. 可追踪性

每条 Must 需求至少连接：

`来源/目标 → Requirement ID → MVP Gap → Acceptance Criteria → Test/验证证据 → Release/结果`

变更只改正文不够，必须同步追踪矩阵、测试、任务和发布说明。

## 8. AI 使用约束

- AI 可做归集、拆解、差错检查、格式化、覆盖面扫描。
- 业务规则、范围、优先级、客户承诺、指标目标、技术工期必须由责任人确认。
- AI 产生的推断必须显式标记并进入待确认；不得为追求文档完整而补全。
