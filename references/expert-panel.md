# 专家团评审编排

## 1. 结论与适用边界

采用“独立评审 → 分歧合并 → 一轮复核 → 责任人裁决”的改良 Delphi 流程。它适合已有 MVP、信息跨产品与技术边界、单一作者容易遗漏的问题；不适合用来替代客户确认、业务 Owner 决策、研发估算或正式安全/法律审查。

默认不为每个小需求召集完整专家团。以下任一成立时启用：

- 用户明确要求专家团或多角色验证；
- 风险为 L2/L3；
- 涉及外部合同/SLA、敏感数据、资金、强监管或不可逆迁移；
- 横跨三个以上系统/团队，或产品、技术、QA 对核心规则存在冲突；
- MVP 基线低置信度，且会显著改变范围、估算或验收。

## 2. 角色配置

固定核心组：

| 角色 | 只回答的核心问题 | 可提出阻塞的范围 |
|---|---|---|
| 产品/业务专家 | 问题、用户、目标、范围、规则和决策权是否清楚 | 核心价值、范围、业务规则、Owner 缺失 |
| C 技术专家 | 基线是否真实、方案是否可实现/估算、依赖与迁移是否明确 | 版本不可定位、接口/数据冲突、重大可行性缺口 |
| QA/验收专家 | Must 是否可测试、AC/测试/证据是否闭环 | Must 无 AC、验收环境或证据不可建立 |

按风险增补：安全/隐私、运维/SRE、数据、法务/合规、客户交付、无障碍或领域专家。PRD Owner/协调人负责组织与归并，但不冒充这些专家或最终决策人。

## 3. 共同证据包

所有专家首轮必须基于同一版本：资料索引、MVP 基线与审计、范围草案、目标 PRD、追踪矩阵、待决策日志。记录 `包版本、基线 Commit/Build、冻结时间`。若首轮材料不同，结论不可直接比较。

敏感信息先脱敏。缺少访问权限时，专家必须标记 `无法验证` 和影响，不得以经验补全事实。

## 4. 两轮流程

### Round 0：设定评审契约

确定范围、风险级别、角色、独立性、提交截止、门禁、证据格式和裁决人。每位专家声明利益冲突及无法覆盖的领域。

### Round 1：独立评审

专家不得先读其他人的意见。每条发现必须包含：

`Finding ID / 领域 / 结论 / 证据ID / 影响需求ID / 严重度 / 建议动作 / 是否阻塞 / 置信度`

严重度只使用：

- `P0 Blocker`：若不关闭，G1/G2/G3 不能通过；
- `P1 Major`：显著返工、验收或上线风险，需 Owner 和期限；
- `P2 Advisory`：非阻塞改进；
- `Question`：证据不足，先进入待确认日志。

### 汇总：去重而不抹平分歧

协调人合并重复项，检查证据，标记共识与冲突。不得用“2 比 1”关闭少数意见。每个冲突记录各自依据、影响和有权裁决者。

### Round 2：定向复核

只向专家回传匿名化/去身份化的发现摘要和证据，不回传职位权威或多数倾向。专家可维持、修订或撤回结论，并说明理由。原则上只进行一轮；出现新证据时可追加一次，不无限讨论。

### 裁决与回填

- 事实冲突：补充取证，由证据解决；
- 业务取舍/客户承诺：业务 Owner 或客户授权人裁决；
- 技术可行性/估算：C 技术负责人确认；
- 风险接受：相应风险 Owner 具名接受；
- 安全/合规红线：由有权专项负责人决定，不能多数票豁免。

PRD Owner 将结论回填到 PRD、追踪矩阵、测试、决策日志和发布范围，再由原提出专家复核关联 ID。

## 5. 门禁与停止条件

专家团给出 `PASS / PASS WITH ACCEPTED RISKS / NOT READY`。满足以下全部条件才可停止并判定通过：

- 所有 P0 已关闭，或通过新证据证明不成立；
- P1 均有 Owner、期限、控制措施和影响需求 ID；
- 产品、技术、QA 三个核心视角均已提交结论；
- 分歧有具名裁决人和决策记录；
- PRD、追踪矩阵与决策日志已同步；
- 风险接受不触碰 Must 范围、核心验收、安全/合规或可恢复性。

任一核心专家缺席、共同证据包版本不一致、裁决权不明或仍有 P0 时，结论只能是 `NOT READY`。

## 6. 防止“专家团表演化”

- 角色数不是质量指标；只邀请能回答明确问题的人。
- 发现必须引用证据和关联 ID，禁止只写泛化建议。
- 专家负责揭示与验证，决策人负责取舍，PRD Owner 负责回填。
- 不要求所有观点一致；保留少数意见和风险接受记录。
- 高风险项目可要求项目外独立专家；低风险内部工具不必强行增加角色。
