## 首轮测试发现与修复

| 缺陷 | 风险 | 修复 | 回归结果 |
|---|---|---|---|
| 来源 ID 中的数字让“体验流畅”被误判为已量化 | 模糊 NFR 可能通过门禁 | 只认可带单位、阈值或明确数量语义的数值 | 通过 |
| 空字段正则跨行读取下一字段 | Owner/来源/目标为空时可能假通过 | 限定空白匹配不跨换行 | 通过 |
| 严格门禁没有因上述模糊措辞失败 | 产生假绿灯 | 修复模糊检测后，门禁模式警告即非零退出 | 通过 |
| 决策表列顺序与阻塞正则不一致 | 正文有阻塞但包级门禁可能假通过 | 改为按表头定位“状态/是否阻塞”列 | 通过 |
| G4/G5 只有文字定义 | 无法证明可验收或已交接 | 增加 Acceptance Ready 与 Handoff Accepted 包级门禁 | 通过 |
| PRD 与清单重复签署 | 两处结论可能不一致 | 清单作为唯一正式签署源 | 通过 |
| 变更单只填需求 ID 即可通过 | 空变更可能进入审批 | 校验 Delta 语义、影响、TASK、签署和日期 | 通过 |
| L2/L3 与专家团生成规则不一致 | 高风险包可能缺少独立评审证据 | L2/L3 自动生成并在包级强制校验专家团记录 | 通过 |
| 两种布局可在同目录共存 | 校验器可能读取新文件而遗留旧基线 | 初始化器和校验器均拒绝布局混放 | 通过 |
| 具名签字被误当成决策正确 | 越权、冲突或无依据决策可能过门 | 增加四类业务决策的授权、证据、一致性、可行性、影响和时效校验 | 通过 |
| 纯 `N/A` 被跨单元格拼接成理由 | 无适用性依据仍可过门 | 要求理由与 `N/A` 处于同一单元格 | 通过 |
| 模板枚举与校验器的空格/下划线不一致 | 用户按模板填写仍被拒绝 | 对空格、连字号和下划线做归一，模板使用统一枚举 | 通过 |
| 专家团只填 `PASS` 即可绕过 | 高风险包缺共同证据或核心视角 | 校验评审契约、三核心视角、P0/分歧和接受风险期限 | 通过 |
| 变更顶部状态与决策表可不一致 | 占位结论被当成已批准 | 强制状态、决策结论、文件名 CHG ID 一致 | 通过 |

## 已验证能力

1. 默认只生成紧凑三件套，项目名替换正确；`--expanded` 仍可生成旧八件套。
2. 默认拒绝覆盖已有交付包。
3. 原样初始化模板草稿为 0 错误、0 警告；开始编辑后缺项仍会提示，Development Ready 门禁不享受模板预警抑制。
4. 缺章节、重复需求、Must 无 AC 均能被阻断。
5. AC 缺 Given/When/Then、不可测措辞会被发现。
6. FR 块不会错误吞入后续章节内容。
7. G1/G2/G3、PRD 状态、阻塞 ID 和成功指标均参与门禁。
8. Must 需求缺 Owner、来源、目标行为或含未决内容时无法过门。
9. 追踪矩阵缺 Test、Owner 或确认状态时无法过门。
10. 完整最小样例校验结果为 0 错误、0 警告。
11. 追踪矩阵引用 PRD 中不存在的 AC 时无法通过候选门禁。
12. `--expert-panel` 只增加一个评审记录，不改变默认三件套；HIGH_ASSURANCE 和 L2/L3 自动启用。
13. Development Ready 现在要求合法交付模式、风险级别、可定位基线、已批准主流程和具名主流程 Owner。
14. Must 需求的完整追踪覆盖来源、目标、GAP、MVP 证据、AC、Test、Owner 和状态。
15. 包级校验已有正向样例，并会阻止缺失产品/需求、C 技术或 QA 具名签署的交接包。
16. 增量变更默认只生成一个变更单，`--expanded` 保留五文件兼容；空 Delta 会被阻止。
17. 包级校验器同时接受新的三文件布局和旧八文件布局。
18. 决策表即使顶部 `BLOCKING_IDS` 误填为空，未关闭阻塞行仍会阻断。
19. `acceptance-ready` 要求构建、测试环境、缺陷、UAT Owner、验收证据和三方签署。
20. `handoff-accepted` 继续要求 UAT、OAT、发布状态、交接阻塞和三方签署。
21. `HIGH_ASSURANCE` 会写入模式、默认 L2 并自动生成专家团记录。
22. 只有需求 ID、没有实际 Delta/影响内容的变更单无法通过。
23. Delta、影响、TASK、三方确认和决策日期完整的批准变更可以通过。
24. 紧凑版与扩展版交接包混放时，即使使用 `--force` 也会被拒绝。
25. 单文件与五文件变更包混放时会被拒绝。
26. HIGH_ASSURANCE 或 L2/L3 缺少专家团记录时，包级校验无法通过。
27. 客户承诺、核心业务规则、技术估算和风险接受均须有有效性校验记录。
28. `UNVERIFIED / INVALID` 会阻断 Development Ready。
29. 核心业务规则和技术估算不能以 `NOT_APPLICABLE` 绕过校验。
30. `VALIDATED` 决策缺授权、来源、约束、可行性、影响、风险或复核条件时无法通过。
31. 客户承诺、核心业务规则、技术估算与风险接受分别执行正式授权材料、需求/AC 追踪、区间/置信度和剩余风险专项检查。
32. 纯 `N/A` 不再被当作非适用理由；理由必须在同一单元格中写明。
33. 客户承诺只有口述证据、风险接受缺控制/复核条件时会被阻断。
34. 专家团通过必须有评审契约、共同证据和三个核心视角完成记录。
35. 变更单文件名、文内 CHG ID、顶部状态和决策表结论必须一致。
36. 模板公开的有条件结论枚举与校验器已对齐。
37. 新生成的 PRD 将状态与 G1–G3 门禁放在文末中文字段表，旧版英文键值仍可校验。
38. 文末 L2 风险等级仍触发专家团强制要求，G1 失败仍阻断 Development Ready。

## BEH-001 前向测试证据

场景：内部“会议纪要自动总结”MVP，转写接口为 Mock，摘要硬编码，只确认“减少整理时间”。

实际结果：

- 没有把登录、权限、存储、监控自动纳入已确认范围；
- Mock 和硬编码被识别为占位，而非已实现能力；
- 成功指标、验收人、范围、数据与权限策略进入待确认；
- G1、G2、G3 均未通过；
- 正确结论为 `NOT READY`，没有降级成 `READY WITH ACCEPTED RISKS`。
